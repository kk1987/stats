# Persistent usage history

Design for exelban/stats#1194, with #3401 (battery trend) and #3450 (network over time). Fork-only (kk1987/stats); upstream takes no contributions, so this ships as an atomic patch stack rebased onto each upstream tag.

Status: shipped — R1 (storage, recorder, settings, battery chart) in fork release 3.0.15.2, R2 (chart, window, presets, export, daily totals) in the next fork release.

## 1. Goals and non-goals

Answer "what was this machine doing at 03:10 last Tuesday, when did it start, how long did it last" across sleep, quit, reboot and app updates, for up to a year. Preserve peaks — iStat Menus averages and admits "it is common for peaks to drop"; the 2026 GPU comment on #1194 is a question about a peak. A disk footprint with a hard, pre-declared ceiling that the user can read off a settings row at any time. Never harm the live app: a full disk, `kill -9`, a panic, a clock step, a second Stats instance or a garbage file degrades history and nothing else. Survive `git rebase --onto vNEW vOLD`.

**v1 lanes.** A *lane* is one recorded scalar series. The v1 set is:

| Module | Lanes | Cardinality |
|---|---|---|
| CPU | `total`, `system`, `user` | 3, fixed |
| RAM | `usage`, `pressure`, `swap` | 3, fixed |
| GPU | `<id>.utilization`, `<id>.temperature` for *every* GPU, not just `selectedGPU` | 2 per GPU |
| Net | `<iface>.up`, `<iface>.down` | 2 per interface ever seen |
| Disk | `<uuid>.read`, `<uuid>.write`, `<uuid>.free` | 3 per volume ever seen |
| Battery | `level` (step), `power` (gauge) | 2, fixed |
| Sensors | every fan, plus a curated list (CPU die, GPU die, battery, ambient), plus whatever the user opts into | ~5 on an Apple Silicon laptop |

**Every percent lane stores a fraction of 1**, because that is what the readers produce — `LoadReader` divides tick deltas by the total, GPU utilization and `battery.level` arrive as 0…1 — so the read side scales once, in `HistoryLaneUnit.format` and in the CSV writer, and the y axis for a percent chart is the whole of 0…1. RAM `pressure` is the one value with no natural unit: the kernel reports three levels, not a scale, so it is stored as the level's position on its own scale — normal 0, warning 0.5, critical 1 — under the `percent` unit. The raw sysctl value (1, 2, 4) is deliberately not what is stored: it is a bitmask that happens to sort, not an ordered scale. RAM `swap` is the swap file's used bytes, a `bytes` gauge and not a percentage of an elastic total.

Plus a **daily network byte counter** (§5), which is *not* a tiered lane — it is a small separate append-only file and is excluded from every lane count and size figure below.

**Lane count is not constant, and the design says so everywhere.** A fresh install on a typical Apple Silicon laptop registers **20–22 lanes**. Lanes then *accrue*: every Wi-Fi → Ethernet → utun → `awdl0` → `bridge0` switch and every USB volume or disk image mounted adds lanes that are kept (LRU-reclaimed, §3, not deleted on unmount — the whole point is that yesterday's data survives today's unplug). A month-old install is realistically **25–45 lanes**. Every size, write-volume and read-cost number in this document is quoted at three points: first launch (~21), a month in (45), and the sensors-heavy worst case (116). The settings row shows **live lane count next to live bytes**, so the user never has to trust a number from a design doc.

**Sensors: curated default, not "what's pinned."** `sensor_<key>_popup` defaults to **true** for every discovered Sensor and Fan (`Modules/Sensors/values.swift:234`, `:295`, verified), so "record what the user pinned" silently enables 50–150 lanes and multiplies the footprint ~5×. v1 records fans plus the short curated list above; everything else is offered as a checkbox in the history window's own sidebar, with no new UI in `Modules/Sensors/settings.swift`.

**Non-goals for v1.** Per-core CPU. CPU frequency/temperature/average-load and every `ProcessReader` — all `popup: true`/`preview: true`, so no continuous source; un-gating costs idle power and is its own patch with a measured number. Process attribution in tooltips (#1207). Bluetooth, Clock, Remote. Widgets access (sandboxed; not worth a second copy). Drag-to-zoom, per-day bars, multi-series normalized overlay (two lines at one pixel height meaning 40 °C and 9 GB misleads). Connectivity shading on the traffic chart (victor-marino) — deferred, named so it is not silently dropped.

**CSV export is in v1.** It rides the read path the chart needs anyway; it answers #1125/#1899/#1952/#2048/#3255 and artstorm's Grafana ask on #630, and it is the only thing that makes a bespoke binary format defensible. Ships with the window, format documented in the same release.

## 2. Sampling

**Hook — one line at `Kit/module/reader.swift:119`**, next to `SystemStats.shared.send`: `HistoryRecorder.hook.ingest(value, reader: HistoryReaderKey(module: self.module, name: self.name), interval: self.interval)`. The whole block is already inside `if let value`, and `interval` is already in scope. Two details earn their place in that one line. `hook` is a locked static that defaults to `shared`: the singleton names the *user's own* history directory, so without a seam the one line connecting every reader in the app to the recorder is the one line no test can execute without writing into it. And `reader:` is an `@autoclosure`, because `Reader.name` is `NSStringFromClass(type(of: self))` split and rebuilt on every access — an eagerly evaluated argument would pay for that string on every tick of every reader in the app with recording switched off.

**Reader identity is passed, not inferred from payload type.** `CapacityReader`, `ActivityReader` and `SMARTReader` are all `Reader<Disks>` (`Modules/Disk/readers.swift:48/173/480`) with independent, partially-filled instances. Type dispatch would write a fake `0 B/s` on every capacity tick and `free = 0` on every 1 s activity tick. Each lane binds to exactly one reader key, and `Modules/Disk/History.swift` is the one conformance that switches on `reader.name`.

**Extraction is typed, not reflective.** `HistoryProvider` is a Kit protocol: `func emitHistory(reader: HistoryReaderKey, into sink: inout HistorySink)`. Mirror is rejected on three counts: `RAM_Usage.usage` and `drive.percentage` are computed properties it cannot see; `GPUs._list`, `Disks._array` and `Sensors_List.list` are private and queue-guarded (a barrier write from the Sensors HID callback on main against a walk on the Repeater queue is a race, not a sample); and a measured 435–542 µs/tick for Sensors is ~10× any sane budget. A typed protocol also fails to **compile** on an upstream rename — for a one-person fork that beats a string path dying silently and getting pruned a year later.

**Conformances live in the module targets — because Kit cannot import them.** Kit imports only system frameworks (verified: `Cocoa`, `Foundation`, `CryptoKit`, `IOKit.ps`, `IOKit.pwr_mgt`, `Metal`, `ServiceManagement`, `SystemConfiguration`, `UniformTypeIdentifiers`, `os`, …, and no module target); the dependency runs modules → Kit, never the reverse. So a conformance for `CPU_Load`, `Disks` or `Sensors_List` *must* live in the module target that defines the type, whatever the access level. (Access level reinforces it for most payloads — `Battery_Usage` is an internal struct, so even its `emitHistory` is internal; `CPU_Load.systemLoad/.userLoad`, every stored `RAM_Usage` field, `Network_Usage.bandwidth/.total` and `drive.uuid/.size/.free/.activity` are all internal, verified. `GPU_Info` is the exception: fully public. The import direction is what actually decides it.) Each module gets **one new file**, `Modules/<X>/History.swift` — still zero edits to any existing `Modules/*` source. No upstream property is made public.

**Ingest allocates nothing on the scalar path.** `guard self.recording` is the first statement, before the dynamic cast, so a reader that emits nothing (Clock's `Reader<Date>`, every `ProcessReader`) costs that guard and nothing else. The guard is **an uncontended `os_unfair_lock` acquisition and a branch**, not a bare load: every reader queue reads that flag — including main, for Battery's IOPS callback — while the settings toggle and `start`/`stop` write it, and an unsynchronized `Bool` shared across queues is a data race whatever its width. Tens of nanoseconds against a per-reader cadence of one second is not a cost worth a race. Past the guard, lanes resolve to **integer ids at registration**, and each module file caches the id it was given, re-resolving only every 600 s — long enough that the hot path is a dictionary lookup, short enough that the registry keeps seeing the lane and LRU does not read a recording lane as cold. The sink is a pre-sized buffer, kept across ticks: no `String` interpolation, no array allocation, no dictionary hashing per sample.

Two locks, in one order. The recorder's guards the sink, the lane registry, the master switch and the clock pair; `emitHistory` runs with it held, which is what serializes a registry that is not itself thread safe. The accumulator table's guards the fold. Ingest takes the recorder's and then the table's; the commit thread takes the table's alone, snapshots and resets under it, and writes with it released.

**Container payloads cost more than a scalar, and the budget says so.** `Sensors_List.sensors`, `Disks.array` and `GPUs.list` are all `queue.sync { self._backing }` returning a **copy** of the whole array (`Modules/Sensors/values.swift:58-61`, `Modules/Disk/main.swift:96-99`, `Modules/GPU/main.swift:71-74`); `Disks.first(where:)` (`:121`) is another cross-queue `sync` per call. `emitHistory` therefore **materializes the array exactly once per tick** into a local `let` and iterates it in place — never one accessor call per lane, and never `Sensors_List.update`, which takes a *barrier* sync and would be strictly worse. The realistic budget is **< 1 µs for scalar payloads (CPU, RAM, Battery, Net), < 50 µs for the container payloads (Sensors, Disk, GPU)**, dominated by the one array copy; §7 says what holds it.

**Cadence and attribution.** Buckets are wall-clock aligned (`floor(epoch / step)`), so readers at 1 s and 60 s share a grid and a runtime `setInterval` is a non-event. A sample is attributed to **every bucket overlapping `[now − interval, now]`** using the reader's own `interval`, so a 60 s CPU interval fills six 10 s buckets instead of leaving five as gaps. The span is clamped to the 16-bucket staging ring below — an absurd interval must not turn one sample into a loop over thousands of buckets — and never reaches behind a bucket that has already been drained. No EWMA: it is wrong precisely at the transients (interface switch, reconnect, wake) users open the window for.

**Step lanes and the bounded hold.** Interval-span attribution assumes the reader ticks on its interval. Battery's `UsageReader` does not: it is an `IOPSNotificationCreateRunLoopSource` with no `Repeater` (verified, `Modules/Battery/readers.swift:30-49`), yet `Module.mount()` calls `initStoreValues` on every reader unconditionally (`Kit/module/module.swift:177-183`), which sets `interval = Double(Store.shared.int(key: "Battery_updateInterval", defaultValue: self.defaultInterval))` = **1 s** (`Kit/module/reader.swift:107-110`). Span attribution would therefore fill exactly *one* 10 s bucket per IOPS event and leave the other minutes as no-data.

So each lane declares a `kind`: **rate**, **gauge**, or **step**. A *step* lane (battery `level`; nothing else in v1) carries `lastValue` and `holdUntil = lastSampleTs + 15 min` in its accumulator. At bucket close, a bucket with `count == 0` whose start is before `holdUntil` is written as `count = 1, min = max = sum = lastValue, reason = HELD`. **No slot-layout change is needed** — `reason:u8` already exists in the 20 B slot and `HELD` is one more enum case, not a format bump. The 15-minute cap is bounded by physics and by the event source: IOPS fires on every 1 % change, on plug/unplug and on sleep/wake, so a genuine 15-minute silence means the level genuinely did not move. The chart draws `HELD` spans dashed and the CSV marks them, so a held value is never presented as a measured one, and a held slot never displaces a measured one: the fold stages the open bucket *before* it synthesizes any hold, and stops one row short of a whole turn of the staging ring.

**`battery.power` is a gauge**, which is what makes it gap honestly — a `rate` would not. A rate lane is not "a lane that gaps": it is a lane whose samples are per-tick *deltas* that the fold divides by the elapsed time since the previous one. `batteryPower` is already an instantaneous wattage, so dividing it is wrong wherever the divisor is not exactly 1 s — and two IOPS notifications inside the same second, which is what plugging the charger in produces, would give `dt = 0.3` and store three times the real wattage at exactly the moment a user opens the chart. A gauge is not held between samples, so it gaps where nothing was measured, and it is stored as measured.

**Rates.** Net `bandwidth` and Disk `activity` are per-tick byte deltas. The recorder divides by the **actual elapsed time since that lane's previous sample, bounded by `interval`** — after a sleep the elapsed time says nothing about the window the delta accumulated over, and dividing a tick's worth of bytes by nine hours would draw a flat zero across the wake. It requires `dt > 0` and rejects non-finite values *before* folding: NaN must never reach min/max, where every comparison against it silently fails. Stored rates are bytes/second.

**Net's substituted zeros: two of three are recoverable, and the third is documented, not faked.** `Modules/Net/readers.swift` hands `callback` a payload in which several distinct conditions all look like `bandwidth == 0`:

1. **Unreachable** (`:221-228`) — `usage.reset()` nils `interface`, so the recorder detects it from the payload and records **no-data**.
2. **Interface change** (`:264-266`) — `usage.bandwidth` is reset and the first post-switch read yields 0. Detectable by diffing `usage.interface?.BSDName` across samples; records **no-data**. The first sample of a launch takes the same path for the same reason: `setup()` zeroes `usage.bandwidth` (`:243`), so there is no previous counter to subtract from.
3. **The over-link-rate guard** (`:299-300`) — `usage.bandwidth.upload/download` are set to `0` *before* `callback` at `:312`, and the raw delta is discarded: `usage.total` is incremented at `:302-303` **after** the clamp, so the bytes are unrecoverable from `total` too. At the hook this payload is **byte-identical to a genuinely idle link**, and there is no way to tell them apart without a new field in `Network_Usage` (`Modules/Net/main.swift:75-109`) or a line in `readers.swift` — both of which §9's zero-edit invariant for `Modules/*/main.swift` and `Modules/*/readers.swift` forbids, in the fork's highest-churn module.

   **Decision: accept it as an unmarked zero.** The damage is bounded: the guard fires on one-shot counter jumps (reconnect), Net's default interval is 1 s, so one clamped sample lands in a 10 s bucket alongside nine good ones — it pins that bucket's `min` to 0 and pulls `sum` down by one sample. It does not create a visible trough at any tier, because T1/T2 roll up from T0 and a single zeroed sample in a 12-sample T1 bucket moves nothing but the min. The escape hatch, if a user ever reports a false zero trough: add `var bandwidthClamped: Bool = false` to `Network_Usage` and set it next to the guard — two lines, two upstream files, listed here so the trade is a decision and not an oversight.

Disk's first activity sample after a mount is the same shape of zero and takes the same trade: `driveStats` leaves the delta at zero until it has a previous counter to subtract from, which is one sample in one bucket, moving that bucket's `min` and nothing else. The Net VPN `/= 2` (`:307-310`) happens upstream of `callback` and is baked in: documented, not corrected.

**Disabled modules and pause.** `Module.disable()` stops the readers; history stops with them — polling hardware the user turned off contradicts the efficiency promise and #3292. But `disable()` is called by both the per-module toggle and the global pause path and posts nothing, making it indistinguishable from a failed reader. The gap taxonomy is therefore collapsed to what is derivable: **`NODATA`, `ASLEEP`, `NOT_RUNNING`, `CLOCK_STEP`**, plus **`HELD`** for step lanes and **`MEASURED`** for a slot that holds a real sample. `GAP_DISABLED` is dropped rather than faked.

## 3. Storage

**Decision: a pre-allocated, row-major, bucket-stamped round-robin archive, committed with `pwrite`, read through a read-only `mmap`.** Not LevelDB — measured, 16 live keys / 92 KB generate ~4.2 MiB of L0 tables every 30–50 min (that is #3292), and an LSM's size is a function of write volume and compaction timing, exactly the property a background feature must not have. Not SQLite — VACUUM, unbounded growth, a second engine.

**Location.** `~/Library/Application Support/Stats/history/`, with `NSURLIsExcludedFromBackupKey` set — continuously rewritten, disposable blocks must not reach Time Machine or be pinned by hourly APFS snapshots. The exclusion is read back rather than assumed: a volume that quietly refuses the key looks exactly like one that honoured it, and failing to exclude is not a reason to stop recording but it is a reason to log it once. **No `$TMPDIR` fallback** (unlike `DB.swift:33-64`): writing a year of history where macOS purges it is worse than not writing it.

**Layout — row-major, one file per tier.** This is the decision all three candidate designs got wrong. A slab-per-lane layout dirties one page *per lane* per flush; at 21 lanes that is ~8 MiB/hour, no better than the churn it claims to beat. Row-major puts all lanes for one bucket contiguous:

```
header    4 KiB   magic "STHS" | formatVersion | step | buckets | lanes
                  | lastCommitBucket | monotonicAnchor | createdTs | crc32
directory lanes × 128 B
          seriesId     16 B   SHA-256 prefix, the stable identity
          module        1 B   enum: cpu|ram|gpu|net|disk|battery|sensors
          unit          1 B   enum: percent|bytesPerSec|bytes|celsius|watts|volts|rpm
          kind          1 B   enum: rate|gauge|step
          flags         1 B   orphan, reclaimed
          firstValidBucket 4 B
          lastUsedTs    8 B
          labelLen      1 B
          label        88 B   UTF-8, truncated on a scalar boundary
          reserved      7 B
matrix    buckets × lanes × 20 B
slot 20 B  bucket:u32 | count:u16 | reason:u8 | pad:u8 | min:f32 | max:f32 | sum:f32
```

Index is `(bucketIndex % buckets) * lanes + lane`. **Every slot stores its own bucket index**, so a stale slot from a previous wrap or a torn write is detectable at read with no header bookkeeping — the "torn write lands beyond `lastCommitBucket`" argument is false in a modular ring (every slot is congruent to some in-window index), and the stamp is what replaces it. Per-lane `firstValidBucket` means a fresh archive reads as no-data rather than a year of flat zeros, without pre-writing NaN; `reason = NODATA` is raw value 0 for the same reason, so the zero-filled matrix a fresh file starts as already means "nothing here" rather than "a measured zero".

**One checksum, chained, over the header and the directory — and one write for both.** Lane identity and geometry are what must not rot silently, while the mutable cursor is self-validating from the slot stamps, so the slots are not checksummed at all. The CRC is chained directory-first, so the directory's own CRC does not depend on the header and can be cached across the commits that leave the directory alone: the common commit path is one 4 KiB `pwrite` with no directory encode. When the directory *has* moved, both go out as a **single `pwrite` of `4096 + lanes × 128` bytes**, never two. Two calls would open a window in which a `kill -9` leaves a header whose CRC covers the new directory sitting next to the old directory bytes, and the next `open()` would read `.badChecksum` and throw away the whole tier — a window hit on every lane registration and on the first commit of every lane, which is a fresh install's normal path. (It removes the process-death window, not a panic, which can still drop some of the blocks one call dirtied.) And a `pwrite` that fails after an earlier run of the same commit has already moved a `firstValidBucket` leaves the directory *owing*: from there on only a header-and-directory write is correct.

**The directory carries a name, not just a hash.** A 16 B hash prefix cannot render "Macintosh HD — free" in a sidebar, cannot group by module, and cannot say what an orphan lane *was*. The entry is therefore 128 B, not 64: `module` drives the sidebar grouping and the filter field, and `label` holds the human string ("Wi-Fi (en0)", "Macintosh HD", "CPU die", the GPU model). Labels are written as `<source> — <metric>` — "CPU — total", "Tim's backup drive — write", "Wi-Fi (en0) — up" — so one string answers both what the lane measures and which of a module's lanes it is, in the sidebar and in the CSV header alike. A sidecar `directory.json` was considered and rejected — it would need its own crash-safety story and could drift from the archive it describes; 256 lanes × 128 B = 32 KiB per tier file is not worth a second consistency problem. The directory is written identically into all three tier files whenever a lane is added (a rare event), which keeps each file self-describing; if a crash between those three writes leaves them disagreeing at open, **T0's copy wins** and the others are rewritten from it, keeping only their own `firstValidBucket` — a lane present in T0 but absent in T2 simply has no T2 data yet, which `firstValidBucket` already expresses. §8 inventories `label` as stored identifying text.

**`sum` + `count`, not `avg`.** Bucket population is not constant — intervals are user-settable 1–60 s and change at runtime, sleep and toggles leave partial buckets, read-side resampling is fractional. Unweighted avg-of-avgs would disagree with the live chart and Activity Monitor exactly around wake and interval changes, and would over-count #3450's daily totals by up to 6×. It is a slot-layout decision, so deferring it costs every user their history; it is made now. `f32` sum carries ~6e-8 relative error — irrelevant.

**Tiers and size.** Per-lane cost is `Σ(buckets) × 20 B`.

| Preset | T0 | T1 | T2 | Slots | Per lane |
|---|---|---|---|---|---|
| Minimal | 10 s / 24 h (8,640) | — | — | 8,640 | 168.75 KiB (0.173 MB) |
| **Standard** (default) | 10 s / 24 h (8,640) | 2 min / 30 d (21,600) | 30 min / 365 d (17,520) | 47,760 | 932.81 KiB (0.955 MB) |

**Two presets, and one of them is the answer.** Standard is the design: a year of history at a resolution that is 10 s for the last day, 2 min for the last month and 30 min beyond that. Minimal exists for the user who wants the live window and nothing retained, not as a different retention policy to reason about. Every number below is quoted for both.

**Sizes at the three reference lane counts (MB, what Finder shows):**

| Preset | ~21 lanes (first launch) | 45 lanes (a month in) | 116 lanes (sensors-heavy) | Ceiling at the lane cap |
|---|---|---|---|---|
| Minimal | 3.6 | 7.8 | 20.1 | 44.3 (256 lanes) |
| **Standard** | **20.1** | **43.0** | 110.9 | **244.6 (256 lanes)** |

Day 1 = day 365 at a given lane count; the only thing that grows is the lane count, and it is capped.

**The lane cap is a flat 256.** It is a structural cap and not a derived one: at Standard's 0.955 MB/lane a 256 MiB budget would allow 281 and at Minimal's 0.173 MB/lane 1,553, so a `min(256, budget / bytesPerLane)` would be the constant 256 in both arms and would only invite a later preset to lift it silently. The worst case any user can reach is therefore Standard at the cap: **244.6 MB**, under the budget with room to spare. At the cap the recorder stops *adding* lanes (existing ones keep recording) and the settings row shows what that lane count costs.

**The 256 MiB budget is an on-disk budget**: it bounds the archive files in `history/`, not the process's footprint — the write path is `pwrite`, so nothing is held dirty in memory, and the query path maps the tier files read-only, so those are clean file-backed pages the kernel may evict at any time. Resident memory is budgeted separately in §7 (< 1 MiB idle, +< 300 KiB with the window open).

Read-side column counts are integer multiples of the tier step (360 at 10 s for 1 h, 720 at 30 s for 6 h, 720 at 2 min for 24 h, 504 at 20 min for 7 d, 1,440 at 30 min for 30 d, 1,460 at 6 h for 1 y), capped by chart width, so the min/max envelope does not stutter at exactly the ranges users stare at. A narrow window only ever *widens* a column, and by a whole number of buckets, so the invariant holds at every width. The 1 y figure is what the integer-multiple rule costs at that range: 17,520 T2 buckets divide by 12 and not by 12.17, so the year is 1,460 six-hour columns rather than 1,440 of uneven width — and 1,460 is therefore the column cap the window's memory budget is quoted at.

**Write cadence.** One `DispatchSourceTimer` for the whole feature: **60 s**, 5 s leeway, `.utility`, private serial queue `eu.exelban.history`, **suspended when no accumulator is dirty**. Each tick closes completed T0 buckets and `pwrite`s the changed row range; T1/T2 rows are written only when their buckets close and are **always rolled up from T0** (min of mins, max of maxes, sums, counts), never accumulated in memory. `F_FULLFSYNC`, falling back to `fsync`, on sleep, on `applicationWillTerminate`, and every 10 min — stretched to 30 min on battery, in Low Power Mode, or at `thermalState >= .serious` (both APIs exist at the macOS 12 target and appear nowhere else in the codebase today; the elapsed test comes first, so the IOKit round trip that answers "on battery?" is paid once every ten minutes and not once a minute). 60 s rather than 30 s halves the write volume at the cost of losing at most 60 s of unflushed accumulator on `kill -9`; for a background feature that is the right side of the trade.

A closed bucket has to live somewhere between the sample that closes it and the commit that writes it, so the accumulator table keeps a **16-bucket staging ring** laid out exactly like the archive's matrix — 160 s, 2.6× the commit cadence and its leeway — and a drain that falls further behind than that loses the oldest buckets rather than growing. That is the trade a background feature has to make, and it is counted rather than hidden: `droppedBuckets` is zero in every intended schedule, and a non-zero value means the commit timer was not running.

**Write volume, derived.** The number is floored by the filesystem block, not by the row size. At 60 s cadence there are **60 commits/hour**; each commit writes 6 closed T0 rows (60 s ÷ 10 s), and APFS allocates in **4 KiB blocks** under copy-on-write, so every commit dirties at least one block regardless of how few bytes changed:

| Lanes | T0 row | 6 rows | Blocks/commit | T0/hour | T1 closes (30/h) + T2 (2/h) | **Total** |
|---|---|---|---|---|---|---|
| 21 | 420 B | 2.5 KiB | 1 (4 KiB) | 240 KiB | 128 KiB | **~0.36 MiB/h ≈ 8.5 MiB/day** |
| 45 | 900 B | 5.3 KiB | 2 (8 KiB) | 480 KiB | 128 KiB | **~0.6 MiB/h ≈ 14 MiB/day** |
| 116 | 2,320 B | 13.6 KiB | 4 (16 KiB) | 960 KiB | 128 KiB | **~1.1 MiB/h ≈ 26 MiB/day** |

**The span sidecar is in that budget too, and it is not free.** `spans.bin` (§4) is rewritten whole, atomically, on every change — one change per sleep, one per wake, one per launch, one per clock step. At a 16 B header and 24 B records, age-capped to T2's 365 days and not line-capped, a laptop that sleeps twenty times a day accumulates ~8,000 records ≈ 190 KiB, and rewriting that on ~40 changes a day costs **~4–8 MiB/day at the tail of the year**, most of it on the last day and close to nothing on the first. That is the same order as the whole T0 write volume above, for a file that exists to answer one question per gap. It is accepted rather than optimized: an append-only sidecar would need its own compaction and its own torn-record story, and the alternative — capping by line count — is the thing §4 refuses, because last month's nine-hour sleep must not be evicted by this month's naps. The number is stated here so it is a decision and not a surprise in a write-volume audit.

(The page-density figure — a 16 KiB page holds 39 T0 rows at 21 lanes, i.e. 390 s of data — describes how *little* is logically written; the block floor is what actually reaches the SSD, and it is the honest number.) The existing LevelDB churn (~6 MiB/hour, dominated by `Sensors@SensorsReader`) is **unchanged** — this store is additive and total process write volume goes up. That goes in the release notes; #3292 is not fixed here.

**Read cost, and why row-major still pays.** Row-major is chosen for write amplification, but it has a real read cost: drawing one lane strides across every row. The bound depends entirely on the range, because only the requested bucket range is touched:

| View | Tier | Rows read | Bytes at 45 lanes | at 116 lanes |
|---|---|---|---|---|
| 1 h | T0 | 360 | 324 KiB | 835 KiB |
| 24 h | T1 | 720 | 648 KiB | 1.7 MB |
| 30 d | T2 | 1,440 | 1.3 MB | 3.3 MB |
| **1 y** | T2 | **17,520 (the whole file)** | **15.8 MB** | **40.6 MB** |

Only the 1-year view reads a whole tier file. Through a read-only `mmap` with sequential page touch that is **~6 ms warm / ~20 ms cold at 45 lanes, ~15 ms / ~40 ms at 116** — inside the 50 ms first-paint budget, and it happens once per range change on the history queue, not per frame. And this is exactly where row-major pays off: that single pass produces the downsampled columns for **every visible lane at once**, plus the min/avg/max table, rather than one strided pass per lane. A column-major layout would read less for one lane and more for the eight the window actually draws, while dirtying 45 pages per commit instead of two. A range the ring provably cannot hold — a 30-day view under the Minimal preset — is not read at all: those columns come back as no-data without a page being touched for them.

**Why `pwrite`, not an mmap store.** `F_PREALLOCATE` does not guarantee in-place overwrite on copy-on-write APFS (snapshot-pinned blocks), so a failed writeback through a writable mapping surfaces as `SIGBUS` — uncatchable in Swift, violating goal 3. A few KiB every 60 s costs nothing and returns `errno`; `mmap` stays read-only for queries.

**ENOSPC is mitigated, not eliminated.** Space is claimed once per tier with `F_PREALLOCATE` — `F_ALLOCATECONTIG` first, falling back to `F_ALLOCATEALL`, because a contiguous extent is worth asking for and a fragmented one is still worth having — and then `ftruncate` to make it the file's size. But the same copy-on-write behaviour that breaks in-place overwrite means an overwrite can still need a fresh block, so **`pwrite` can return `ENOSPC` (or `EDQUOT`) at any time**. Claiming preallocation makes steady-state writes "near-immune" while also arguing CoW breaks in-place overwrite is incoherent; it is dropped. The actual mitigations are two:

- **A free-space precondition.** `volumeAvailableCapacityForImportantUsage` is read every tenth commit (~10 min) and after any failure. Below **50 MB free** the commit is skipped, recording is marked paused and settings shows "History paused — low disk space". A volume that cannot be queried is "unknown", never "full": refusing to record because a `stat` failed would be the store harming the feature it exists for. The store degrades before the volume does.
- **Three strikes.** Three consecutive write failures suspend recording for an hour, surface the same banner, and retry on the next cycle rather than waiting for relaunch.

**Corruption.** A file that cannot be *examined* — a transient `errno` from `open`, `pread`, `fstat` or `mmap` — is left exactly as it is, because the bytes may be perfectly good and only the attempt went wrong; quarantining on an `EMFILE` would destroy a year of history over a descriptor leak somewhere else in the app. A file that can be examined and is wrong is renamed to `t0.rrd.corrupt-<ts>` (one kept) and recreated empty. The damage set is: bad magic, a bad header CRC, an unknown `formatVersion`, a **geometry that is not this tier's**, and a file **too short** to hold what its own header claims. The last two matter as much as the checksum, because the stored lane count drives every offset in the file: it has to be sane before anything is sized from it, and the file has to be long enough before a mapping is taken over it. Inside a valid file a garbage slot is bounded by its stamp and reads as no-data; every read is bounds-checked. Lane identity and geometry are CRC'd once, while the mutable cursor is self-validating from slot stamps, so a torn header write cannot discard a year. **CRC-32 is ~25 lines of Swift in the archive file** (lazily built 256-entry table) — there is no zlib import anywhere in the project and Kit's umbrella header (`Kit/Supporting Files/Kit.h`) carries only `lldb.h`; adding `#include <zlib.h>` there would be an unlisted upstream edit to buy an algorithm that fits on one screen.

**Cross-process exclusion.** `flock(LOCK_EX|LOCK_NB)` on `history/.lock` at startup; the loser records nothing, logs once, **and shows "History is being recorded by another copy of Stats" in the settings section** — this fork routinely runs a locally signed build beside the released one, so two writers is normal here and a log line nobody reads is not an answer. Only `EWOULDBLOCK` means a second instance: an unopenable lock file is our own problem and must not be reported as somebody else's copy. The lock is also the gate on every destructive path — delete and preset change both refuse when this process does not hold it, because unlinking the winner's archives would spend its disk without freeing it.

**Crash and restart continuity — coarse tiers catch up at open.** Because T1/T2 are computed from T0 at close rather than accumulated in memory, a bucket that straddles a relaunch is still correct when it closes: the closing rollup reads the whole T1 span out of T0, including the part written before the quit. What remains is buckets that closed *while the app was down*. Stats quits on every update and every reboot, so without a fix the 30-day and 1-year views — the entire point of #1194 — would develop a hole at every restart.

**On open, for each coarse tier, every bucket newer than that tier's `lastCommitBucket` and older than the current one is rolled up from T0 and written.** T0 retains 24 h, so any downtime shorter than that is fully recoverable; the work is bounded by one pass over ≤8,640 T0 rows producing ≤720 T1 and ≤48 T2 rows — single-digit milliseconds, on the history queue, before the first live commit. It is the same routine the steady-state close runs, differing only in how many buckets are outstanding, and a span that rolls up to nothing records that it was scanned so the next tick does not scan it again. Downtime longer than 24 h leaves the unrecoverable span as honest no-data. Unit-tested, and on the manual matrix ("quit mid-bucket, relaunch, 30-day view has no hole").

**Versioning.** No in-place migrations, ever: a `formatVersion` bump renames archives and starts fresh. **Adding a lane never bumps the version** — a lane is a directory entry, and lane growth is a copy-forward rebuild (slots carry their bucket index, so the copy is a straight row-for-row transfer into the wider stride, with the new lanes left zeroed), so per-core CPU, more sensors and per-volume Disk land later as purely additive patches. The rebuild stages into `t<n>.rrd.rebuild` and lands with one `rename(2)`; an orphan left by a `kill -9` between the two is swept at the next `open()`, because a full-size file nothing ever reads again is exactly what the declared ceiling forbids.

**Preset changes.** With two presets there is exactly one transition each way. *Growing* Minimal → Standard leaves T0's file untouched — "copies T0 forward" costs nothing at all — and then runs the same catch-up rollup over the retained 24 h to populate T1 and T2, so the new tiers start with **24 h of data and nothing before that**, which the chart shows as no-data rather than as zeros. *Shrinking* Standard → Minimal unlinks T1 and T2, behind a Delete-weight confirmation that names what goes. Either way ingest is quiesced first, what the accumulators already hold is committed rather than discarded — a preset change is not a delete, and a grow that dropped the last minute of T0 would roll that hole straight into the new tiers — and the mappings come down before any file is unlinked.

**Lane lifecycle.** Lane cap as above, reclaimed by **LRU on `lastUsedTs`**, not a 365-day TTL — `utun*`, `awdl0`, `bridge0`, disk images and replugged volumes churn identities fast enough to exhaust a TTL-only directory. A lane has to have been idle for **24 h** before its slot can be handed to a new identity: LRU alone would let a machine whose lane set genuinely exceeds the cap evict and re-register the same lanes on every tick, shredding a day of data per round trip, and a floor turns that into an honest refusal instead. `lastUsedTs` moves on every commit and deliberately does not dirty the directory, so the recorder writes the directory out **once an hour regardless** — otherwise a lane that has been recording all week could look reclaimable at the next launch and lose its data to a reclaim. Identity keys are the most stable available: volume **UUID** (not `BSDName`), SMC **key** (not label), `GPU_Info.id` (not `model`, which collides on dual identical GPUs; `GPUs` has no `name` field). An **orphan** lane — one whose source has not been seen this launch — shows greyed in the sidebar with its stored `label` and a last-seen date from `lastUsedTs`, which is what the 128 B directory entry is for. The `reclaimed` flag is deliberately *not* a reason to grey: it marks the id that was handed to a *new* identity, so the lane wearing it is the one actively recording, and greying it would grey the newest lane on the machine; it is retired as soon as that lane writes a bucket of its own, because `firstValidBucket` then says the same thing more precisely. **Disk lane labels store the volume name exactly as macOS reports it** ("Macintosh HD", "Tim's backup drive") — not anonymized, not shortened to the UUID that is the actual identity: a lane whose drive was unplugged last month has to stay recognisable in that sidebar, and a 16 B hash is not. §8 inventories it as stored identifying text.

**Updates and rebase.** `Kit/scripts/updater.sh` replaces only the bundle, so `history/` survives; `Kit/scripts/uninstall.sh:37` already removes the parent. The archive is entirely new files, so a rebase cannot touch the format.

## 4. Time handling

Buckets are indexed by **wall clock** (UTC epoch seconds) — the point is answering "at 03:10 yesterday". Time zones and DST are rendering concerns; every real UTC offset is a multiple of 15 min, so the 2-min and 30-min tiers stay aligned to local wall clock (Nepal's +5:45 puts local midnight mid-bucket at T2; accepted).

`mach_continuous_time()` is read alongside the wall clock **at ingest, inside the bucket-index computation** — not once per commit, which would let accumulators land in the wrong bucket for up to a full period. *Continuous*, not absolute: it counts through sleep, so a nine-hour sleep advances both clocks together and only a clock that was genuinely *set* shows up as divergence. The pair is re-anchored on every reading rather than on every step, so `ntpd`'s few milliseconds a minute never accumulate across the 2 s threshold and report a step that never happened. Divergence over 2 s means the clock stepped.

A **forward** step needs no action on the archive: the ring advances and the skipped slots read as no-data by their stamps. It does get a span, because "Clock changed" is otherwise indistinguishable from "nothing was recorded", and a span is a line in a sidecar rather than a pass over a ring. A **backward** step never overwrites a slot whose stamp belongs to the pre-step era — `lastCommitBucket` never moves backwards, so it is the high-water mark of every era the archive has lived through, and a row at or below it whose ring cell already carries that exact stamp is dropped. In forward-running time that check is one `UInt32` compare per commit and no stamp reads at all. A step larger than a tier's window **resets** that tier rather than interleaving two eras — which is the same condition as a gap at or beyond the tier's capacity, and is handled by the same code: the file is recreated, so `ftruncate` gives the all-zero matrix for free and the only bytes that reach the disk are the header and the directory.

**What that costs, said out loud: a backward step stops recording — on every tier — for its own length.** The re-lived buckets are precisely the ones the pre-step era stamped, so every row a commit produces while the wall clock is walking back over them is dropped, T0 included, until the clock passes the high-water mark again. A clock set back an hour is an hour of no-data with "Clock changed" as the reason, not an hour of data written twice. The alternative is two eras interleaved in one ring with nothing in a slot saying which era it belongs to, which is worse than a labelled gap — and the case is rare enough (a DST transition does not move the UTC clock at all; this is someone setting the clock, or NTP correcting a badly-drifted one) that a more elaborate answer would be paying for something nobody sees.

**Gaps are derived at read, never backfilled at write.** With stamped slots, "Stats was not running" and "asleep for nine hours" follow from `lastCommitBucket`, `firstValidBucket` and the `NSWorkspace.willSleep/didWake` spans the recorder keeps in a small sidecar — a 16 B header and 24 B records, age-capped to T2 retention and not line-capped; §3 carries its write cost. The observers fire **on main**, which is where the sidecar is written: it is one small file rewritten atomically, the encode happens under the monitor's lock and the write with it released, and a sleep notification is delivered with time in hand for exactly this. A `willSleep` also commits what the accumulators hold and flushes, then gives the timer up, because a timer left armed across a nine-hour sleep is a wakeup the feature does not need.

**A process closes only the sleep it opened itself**: a span left open on disk is one the previous process never saw the end of — powered off, battery flat or force-rebooted while asleep — and it is dropped at load rather than restored, because a later wake closing it would produce an "Asleep" spanning days the machine was demonstrably awake. Next to nothing is lost: the launch's own span already covers the whole stretch. That one is written from `lastCommitBucket` to now as **`NOT_RUNNING`**, or as **`CLOCK_STEP`** when the stored monotonic anchor says the two clocks disagree about how long the app was down — which is the better answer of the two anyway, and is what the anchor in the header earns its bytes for. (The comparison is good to a commit period plus a bucket plus the 2 s threshold, and nothing finer is claimed; every clock change worth catching is minutes or hours.) The exceptions are an install that never committed, where there is no last commit to date a span from, and a hole shorter than two T0 buckets, which no column can show. There is no app-wide sleep/wake observer today — the only ones live in `Modules/Sensors` and `Modules/Bluetooth` (verified) — so the recorder registers its own, in its own new file. Backfilling at launch would dirty multiple MiB in one burst at the worst moment for battery; a gap at or beyond a tier's capacity resets the tier instead of iterating a full ring.

Order settles which reason a bucket gets: a recorded slot answers for itself, then a lane's `firstValidBucket` — before any span, because "asleep" is not why a lane that did not exist yet is empty — then the most specific covering span, then `lastCommitBucket`, then no-data. Spans overlap in one real case, the machine slept and was shut down while asleep, and a clock step beats asleep, which beats not-running. A range is resolved in one merge walk of the sorted spans against the sorted buckets rather than one scan per column: O(columns + spans) against O(columns × spans), which at 1,440 columns and a year of accumulated sleeps is what keeps it inside the 50 ms first paint.

Gaps are **not interpolated across**: a 45° hatch in `separatorColor`, and the hover readout says it in words — "Asleep 02:14–08:31", "Stats not running", "Clock changed". `HELD` spans (§2) are drawn dashed with "Last known value" in the readout. That sentence is what turns a hole into an answer to "when did it start, how long did it last".

So instead of restructuring two module popups into stack views (~20 lines each, in files upstream actively edits), **the free function gains a `button: NSView? = nil` parameter** — `rightInset` already carves out exactly the space it needs, so the button is `addSubview`d, pinned to `view.trailingAnchor`, and `rightLine` pins to its leading edge. That is ~19 lines in one stable function, and each popup call site then takes **one added argument**, not a structural swap. A new optional parameter with a default is about the most rebase-friendly upstream edit available; both costs are listed in §9. Secondary: a "History" row in the Settings sidebar. It is a **launcher, not a pane** — the window is its own window, not a 540 pt settings view — so the row opens it and hands the sidebar selection back to whatever was open, on the next run loop turn, because the selection notification is posted before the row paints its own highlight. **No popup-header button**: `HeaderView` pins the title width as `frame.width − activity.intrinsicContentSize.width − settings.intrinsicContentSize.width` (`Kit/module/popup.swift:423-427`), so a third button edits that constraint rather than appending, conditional visibility makes title centering differ per module, and it would appear in all ten modules while working in six. The shortcut is **⌃⌥H** (⌥⌘H is Hide Others), a new branch in `Stats/helpers.swift:372-376` — listed in §9, not hidden.

**Window.** `HistoryWindow` in Kit (the only place every module target reaches), resizable, min 760×460, frame in `Store` (so "Reset settings" forgets it too), opened with `NSApp.activate(ignoringOtherApps: true)` — the app is `LSUIElement` and every other window path does this. One instance, kept alive across closes, because the sidebar selection and the range are what the user was last looking at. Left sidebar of lane checkboxes **grouped by the directory's `module` byte and labelled from its `label` field**, with a filter field and a default selection (the originating module's primary lanes, skipping orphans — required once 100+ lanes exist). "Primary" is expressed in what the directory actually stores, which is the unit and not the metric name — percent for CPU, RAM, GPU and Battery, bytes/second for Net and Disk, °C for Sensors — and that picks the right lanes: RAM's usage and pressure over its swap byte count, GPU utilization over GPU temperature, disk read and write over the free-space gauge. **Eight lanes at once**, which is the number §7's memory figure is quoted at and therefore the number the sidebar enforces: a ninth check beeps rather than drawing a ninth line on one shared y scale. Below the lanes, the sensors the machine could record and v1 does not: the per-lane opt-in from §6, in the one place every lane is already enumerated. Top bar: range control (1 h / 6 h / 24 h / 7 d / 30 d / 1 y), min/max band toggle, Live/Pinned toggle, **Export CSV**. Then the chart, a time axis, and a right-hand table of each visible lane's min/avg/max that switches to the value under the crosshair.

**Chart.** `HistoryChartView`, in `HistoryChart.swift`, subclasses **`NSView`**. Subclassing the existing `ChartView` base was the plan and is not available: its designated initializer and its `write{}`/`onMain{}` state-queue helpers are `fileprivate` to `Kit/plugins/Charts.swift`, and the chart needs neither — everything expensive already happened on the history queue, which hands it columns and never the decoded series, so it holds no queue of its own and is main-thread only. `LineChartView` is deliberately not reused either: index-based with uniform x spacing, an O(n) scan-and-sort in `intervalStatsLocked()` on **every** append, 600 points max, a hardcoded `0/25/50/75/100` percent ladder against a per-draw rolling max, and a hardcoded `HH:mm:ss` axis with no setter — six of the v1 lanes are not 0…1, and a 30-day view whose five x labels all read "14:32:05" answers nothing. `HistoryChartView` is **time-indexed**: range → pixel columns, coarsest tier finer than one column, a min/max band at 25% alpha under a solid avg line, **y axis in real units per lane** (bytes/s, °C, W, %) and **x axis with dates** on 7 d / 30 d / 1 y. Lanes that do not share a unit share the scale and lose the unit suffix — a °C lane against a bytes lane really is flat at the bottom, and saying so beats normalizing. The hatch marks the columns *no* drawn lane has a sample in, not each lane's own gaps: per-lane gaps are already visible because the line stops, and four overlapping textures on a four-lane chart are not information.

**Interaction and cost.** Crosshair on hover; ←/→ one column, ⇧←/→ ten, `1`–`6` ranges, Home/End, Esc (crosshair first, window second), Tab into the sidebar filter and ⇧Tab back out the same door. Lane geometry is cached in paths rebuilt only on a range, selection or size change, and the crosshair draws in its own layer so scrubbing does not rebuild every band per mouse event. Tracking areas **drop `.activeAlways`**; the live-refresh timer is gated on `NSWindow.occlusionState` (the precedent is `Kit/module/module.swift:309`), since `isVisible` is false only for miniaturized or ordered-out windows and a window behind Xcode would otherwise poll forever — and it ticks at the range's own cadence, 10 s for the short ranges up to 5 min for a year, because re-reading 40 MB of T2 every ten seconds to move a year-long chart by nothing is the poll that gating exists to avoid. Pinned freezes the end of the range, so there is nothing to poll for at all.

**Battery gets a popup line chart.** `Modules/Battery/popup.swift` had only a `BarChartView`. A ~40-line "Usage history" section with a `LineChartView` fed from `battery.level` is the highest value-per-line item in the feature and the only thing that makes a #3401 user see any change in the surface the issue names.

**#3450 gets a real surface.** The Network section shows today's and yesterday's upload/download totals from an **independent monotonic per-day byte accumulator written at ingest** — not integrated from averaged buckets, and not `Network_Usage.total` (which the user's own reset schedule zeroes). Days roll at **local midnight**, recomputed from the current calendar on every commit tick rather than from a cached `+86400`, so a DST boundary produces a 23- or 25-hour day rather than a shifted one and a timezone change re-anchors immediately. Bytes that arrive after the day's end but before the next roll are held aside and attributed by that roll, which is what keeps the calendar off the ingest path without misdating a minute of midnight traffic. The two rows carry a tooltip saying what they exclude — sleep, app-off time and the reader's substituted zeros — so it reads slightly below both the ISP figure and the Net popup's own counter two inches away. The view lives in `Modules/Net/History.swift` and refreshes itself off the in-memory counter, so the upstream popup file gains exactly one `addArrangedSubview`.

Days are keyed by their **local calendar date** (`YYYYMMDD`) rather than by the epoch second their midnight fell on, which is what survives a flight: yesterday is still the same Tuesday in New York as it was in Berlin. `history/daily.bin` is append-only — a 16 B header and 24 B records of `day | up | down | crc32`, the last record for a day superseding the earlier ones — so a torn last record is dropped at load by its length or its checksum and the file is rewritten rather than appended onto at a misaligned offset. It rides the commit tick and has no timer of its own, but writes at most **once every 5 minutes** plus on a day roll, a sleep, a flush and a terminate: an append dirties a 4 KiB block whatever it writes, and every-minute durability for two numbers would cost ~5 MiB/day, the same order as the whole T0 write volume. At five minutes it is ~1 MiB/day and a `kill -9` costs the last five minutes of a figure that already says it undercounts. It is compacted to one record per day once it passes 2,000 records, keeps a 400-day tail, and at under 10 KiB it is inside the directory the settings row sums and outside every lane count.

**Popup restore is deferred, not faked.** `setPoints` is `public func setPoints(_ newPoints: [DoubleValue])` (`Kit/plugins/Charts.swift:671`) — non-optional, so it cannot express a gap; and the first live `addValue` derives `typical` from the restored 10 s spacing and nils out up to `n−1` slots, erasing the restore within one tick. If it ships it ships as a `setPoints([DoubleValue?])` overload, a freshness guard (`now − lastBucket < 2 × step`), and resampling to the live cadence with explicit nils for the pre-launch portion. Trading a blank chart for a wrong chart is not a win, so v1 edits `Charts.swift` not at all.

**The CSV format is a public contract.** Export writes the visible range and the checked lanes — the plan the window was showing, not one re-planned against the clock while the save panel stood open — as one row per drawn column, UTF-8 without a BOM, CRLF line endings, RFC 4180 quoting (a cell holding a comma, a quote or a line break is wrapped in quotes and its own quotes doubled), and no preamble: the RFC has no comment syntax, so a metadata block above the header line is a parse error in the tools this exists for. The first field is `timestamp`, the column's start in ISO 8601 with a numeric UTC offset (`2026-09-14T03:10:00+02:00`) — local time, because the question is "what was this machine doing at 03:10 last Tuesday", with the offset spelled out so a row on a DST boundary is still unambiguous. Then three fields per lane, `<label> min (<unit>)`, `avg` and `max`, the same three the readout table shows; then one `gap` field. Values carry **two decimals, `.` as the decimal separator and no thousands separator whatever the app's locale is** (`en_IN` writes 12,345.50, which is one value in two cells; `ne_NP` writes Devanagari digits) and are in the unit the lane was **recorded** in, not the one it is displayed in: percent as 0–100, rates as bytes per second un-prefixed, temperatures in °C even when the app shows °F — a file whose numbers change meaning with a display setting is not a contract. The formatter's locale is pinned to `en_US_POSIX` for the same reason the separator is: a fixed `dateFormat` alone would still let `th_TH` date these rows in the Buddhist era. A lane with nothing in a column contributes three empty fields and never a zero, and a non-finite value exports as an empty cell. `gap` is empty for a measured row and otherwise `held`, `asleep`, `not_running`, `clock_step` or `no_data`; it describes the row rather than the cell, so a lane holding its last level while another is being measured does not show there — the alternative widens every lane by a third for a field that is empty in all but a handful of rows. The header tokens and the gap vocabulary are fixed English; only the suggested file name ("Stats history 24 hours.csv") is localized, because it is a file name and not a cell.

**Theme, localization, accessibility.** Semantic `NSColor`s plus one system colour per module, shaded toward grey for the second and later lane of the same module — there is no `<Module>_color` key in this codebase, colours are stored per *widget* as `<Module>_<widget>_color` and a lane belongs to a module, not to a widget; the shade is deferred into a dynamic colour so both operands resolve against the drawing appearance, and `viewDidChangeEffectiveAppearance` redraws. **57 new strings**, registered in all **41 `.lproj`** (523 identical keys each) via `Kit/scripts/i18n.py fix`, so every key exists everywhere and a locale renders the English until its translation lands — the module group titles and `"Chart history"` were already translated and cost nothing new. Lane `label` strings are device identifiers and are not localized. New controls are named **"Stored history"**, never "Chart history", which already means 60–600 points of live ring two rows away. Sidebar and readout table are natively accessible; the chart exposes one element per visible lane plus a summary naming range and lane count, built with the columns rather than with the paths, so a VoiceOver query that arrives before the first draw — or while the window is occluded, which is exactly when the refresh timer is gated off — still finds something to read.

## 6. Settings

One "Stored history" section in App settings — **no per-module checkbox in the ten `Modules/*/popup.swift` settings and no per-sensor checkbox in `Modules/Sensors/settings.swift`**. The argument is not "that would be 11 extra upstream files" — §9 already adds one line to five of those popups for the expand button, so the file count is not the objection. The objection is that **per-lane opt-in belongs where the lanes are enumerated**: the window sidebar already lists every lane with its module, label and last-seen date, and a per-sensor mirror in `Modules/Sensors/settings.swift` would be a 100+ row table duplicating it, in the layout code upstream churns most. Checking the box there is the whole mechanism — the next tick of the sensor's own reader sees it, registers the lane and starts folding — and unchecking it stops the samples and leaves what was recorded alone until the LRU reclaims it, which is what makes turning a sensor off and on again cheap.

- **Master switch — ON by default** (`history_state`). A retrospective feature that is off when the anomaly happens is worthless; the #1194 GPU comment is someone who wanted data he did not have. Defensible only because of §3's numbers: ~20 MB at first launch, 43 MB at a realistic month-old lane count, a hard 244.6 MB ceiling, ~8.5 MiB/day. Off means zero ingest and zero writes, from launch: the stored preference is what `start()` reads, not something applied when the settings panel is first opened. **This switch ships in R1, in the same release as the recorder** (§10) — shipping the hook without it would leave R1 users with a growing directory and no in-app way to see, stop or delete it.
- **Live readout: "N lanes · X MB"**, with the real path as tooltip and **Reveal in Finder**. Lane count next to bytes, because lane count is the variable that moves and no fixed number in a settings string can stay true. Allocated size, not logical — that is what Finder shows and what the ceiling is quoted in, and the tier files are preallocated, which is exactly the difference. Read off main, because a settings panel is not an exception to "nothing blocks main on I/O".
- **Retention preset** (`history_preset`) — two entries: Minimal (24 h) and Standard (default; 24 h + 30 d + 1 y). Each entry carries the projected size **from the current lane count**, so the user compares the two before choosing rather than after; with no lanes registered the entries are bare names, because a projection of two file headers is a true number answering the wrong question. Growing copies forward and rebuilds what it can (§3); shrinking discards behind a Delete-weight confirmation that names what goes. The preference is stored unconditionally and the live change can decline — another copy of Stats holding the flock is a normal state in this fork — with three outcomes the alert distinguishes, because a user whose coarse tiers were already unlinked must not be told the retention "could not be changed". **R2** — a preset picker is not a kill switch and can wait.
- **Delete history** — quiesces ingest, drops the staged rows, munmaps and closes every archive on the history queue, unlinks, recreates empty. Never truncates a mapped file. The `flock` is deliberately kept across the whole sequence, so a second copy of Stats cannot slip in between the unlink and the reopen, and the master switch is not touched: a user who deletes their history is not asking to stop recording it. **R1.**
- **Status banner** for the three states that are not "recording": paused for low disk space, suspended after three write failures, and "History is being recorded by another copy of Stats".
- `AppSettings.resetSettings()` (`Stats/Views/AppSettings.swift:443-459`) calls `Store.shared.reset()` then `restartApp(self)`; `HistoryRecorder.shared.deleteAll()` goes **between** them and completes synchronously before `restartApp`, or the delete races the relaunch. Its confirmation text says history is deleted too.

## 7. Performance and battery budget

| Path | Thread | Budget | How |
|---|---|---|---|
| `ingest`, scalar payloads (CPU, RAM, Battery, Net) | reader queue, incl. **main** for Battery/Bluetooth | < 1 µs | uncontended `isRecording` lock and branch, cached integer lanes, arithmetic, no allocation, no I/O |
| `ingest`, container payloads (Sensors, Disk, GPU) | reader queue | < 50 µs | **one** `queue.sync` array materialization per tick, then in-place iteration |
| commit | private serial, `.utility` | < 2 ms/tick | drain under the table's lock, `pwrite` with it released |
| catch-up rollup at open | private serial, `.utility` | < 10 ms, once | ≤8,640 T0 rows → ≤768 coarse rows |
| wakeups | — | 1/min, 5 s leeway, suspended when idle | one timer for the feature |
| disk | — | ~0.36 MiB/h (21 lanes), ~0.6 (45), ~1.1 (116) | block-floor derivation in §3; `fsync` 10 min, 30 on battery/LPM/thermal |
| memory, idle | — | < 1 MiB | ≤64 B/lane accumulators (< 16 KiB at the cap) plus the 16-bucket staging ring (80 KiB at the cap) and the header and directory pages |
| memory, window open | — | **+< 300 KiB, range-independent** | ≤1,460 columns × 16 B × visible lanes (8 lanes ≈ 182 KiB, and 8 is the cap the sidebar enforces); the decoded tier read is streamed into columns, never retained |
| window first paint | main + read queue | < 50 ms | aggregate to pixel columns **on the history queue** (read cost table, §3); hand main ≤1,460 columns × visible lanes, never the decoded series |

The loaded-window memory figure is the same for a 1-hour and a 1-year view — that is the point of aggregating to columns on the read queue. Only the *transient* read buffer differs, and it is consumed page by page rather than materialized (40.6 MB of T2 at 116 lanes is mapped, not copied).

Every number above except the two ingest budgets is derived in §3. The ingest budgets are held **by construction** rather than by a timer in the suite: the lane id is resolved once per source and cached for 600 s inside the module file, the container payloads materialize their array exactly once per tick, and the sink keeps its capacity across ticks. What `Tests/History.swift` pins is the geometry the rest of the table is derived from — the accumulator at ≤64 B and the drawn column at ≤16 B, the 20 B slot, the 128 B directory entry, the 4 KiB header, the lane cap and the three tier steps — so a later change to any of them fails there rather than in a user's archive. The 435–542 µs Mirror figure and the 76 µs lane-hashing figure that shaped the module-side lane cache are design-time measurements and are recorded in the files they shaped; nothing in the suite asserts a duration.

No new sampling timers — every sample rides a reader tick that already fires. Chart redraw stays on main but reads an off-main snapshot, matching the `Charts.swift` convention. Nothing blocks main on I/O.

## 8. Privacy

Stored: numeric series plus identifiers — SMC keys, GPU ids and models, volume UUIDs, BSD interface names (`en0`), and the directory's **`label` field**, which holds the human-readable name of whatever the lane measures: volume names ("Macintosh HD", "Tim's backup drive"), interface descriptions ("Wi-Fi (en0)"), sensor labels and GPU models. That is the same class of text already written to `~/Library/Application Support/Stats/` by the existing store, and it is what makes the sidebar and orphan display possible (§3). The two sidecars hold no identifiers at all: `spans.bin` is timestamps and a reason byte, `daily.bin` is a date key and two byte counters. **Not** stored: SSIDs (`wifiDetails` excluded outright), IP addresses (`laddr`/`raddr` excluded), DNS servers, hostnames, process names, user accounts, Bluetooth device names. Nothing is transmitted — `SystemStats.send` and Remote are untouched and never fed from the store. Deletion: the Delete button, "Reset settings", `rm -rf ~/Library/Application Support/Stats/history`, or the existing uninstaller. The directory is excluded from Time Machine.

## 11. Risks

1. **The format is wrong and we find out after users have data.** Accept. No-migration policy costs history once; R1-before-R2 surfaces it early, lane growth is already a copy-forward rebuild, and the widths are pinned by a test so a change to one is a decision rather than an accident.
2. **Lane count, not preset, is what drives footprint** — and it grows with the user's habits, not with time. Mitigated by the 256-lane cap (244.6 MB at Standard, the worst case anyone can reach), LRU reclaim behind a 24 h idle floor, and a settings readout that shows live lanes and live bytes rather than a number from this document.
3. **Sensors cardinality.** Curated default, per-lane checkboxes in the window sidebar, lane cap at creation, and a preset picker that projects the cost at the live lane count before the user commits.
4. **Lane identity drift.** Volume UUID, SMC key, `GPU_Info.id`; LRU reclaim on `lastUsedTs`, written out hourly so the stored value cannot fall far enough behind to make a hot lane look cold; orphans greyed with their stored label and a last-seen date.
5. **`SIGBUS`.** Eliminated on the write path by `pwrite`; read mappings hold their descriptor for the process lifetime, are never truncated, and tear down on the history queue before any unlink.
6. **`ENOSPC` is not eliminated**, only mitigated — preallocation reserves the extent but APFS copy-on-write can still need a block. The free-space precondition and the three-strikes suspend are the real answer; a user on a genuinely full volume gets a paused banner, not a corrupt archive.
7. **`f32` precision on large byte counts.** Accept; ~6e-8 relative error beyond 2²⁴.
8. **Typed `emitHistory` means 7 new module-target files.** Accept — Kit cannot import module targets, so there is no alternative that compiles, and a compile error on an upstream rename is the feature, not the cost.
9. **Total process write volume goes up**, because the LevelDB churn is untouched. Stated in settings copy and release notes; #3292 remains open.
10. **Battery sampling stays event-driven.** No dedicated timer: interval-span attribution plus the 15-minute `HELD` hold on the `level` step lane (§2) turns irregular IOPS events into a continuous series, drawn dashed so a held value is never mistaken for a measured one; `battery.power` is a gauge and gaps wherever nothing was measured.
11. **Net's link-rate guard is an unmarked zero** (§2). Bounded to one sample per firing and invisible at T1/T2, but it is a known small lie in the data. The two-line upstream fix is specified in §2 and deliberately not taken: the zero-edit invariant for `Modules/*/readers.swift` is worth more to this fork than marking a zero that moves only a bucket's `min`.
12. **CPU temperature and frequency have no history at all** and will be the first thing asked for. The sidebar lists what was recorded, so their absence is silent rather than explained — un-gating them is a v2 patch with a measured idle-power number, and a row that exists only to say "not recorded" would be the wrong half of that patch.
